## 4. Копирует ли Ozon фото к себе

- В документации `zorko/docs/ozon/` об этом ничего нет (там только: `/v1/product/pictures/import` отключён 01.10.2026,
  замена — `/v2/product/pictures/import`; `/v2/product/pictures/info` — фото товара).
- Косвенно — да: витрина Ozon отдаёт фото с собственного CDN `ir.ozone.ru/s3/multimedia-…` и `cdn1-3.ozone.ru`
  (магазин берёт их оттуда: `setra-parts-timeweb-app-v0.13.2/src/ozon-media.mjs`, `src/photo-import-manual.mjs`).
  Значит, покупатели видят копию на серверах Ozon, а не GitHub.
- **Не подтверждено:** какие адреса возвращает `/v2/product/pictures/info` (копию Ozon или исходную ссылку GitHub) и
  перекачивает ли Ozon фото при повторной отправке. Это важно: `korrektor_more.py фото` и `/v3/product/import`
  (`korrektor_apply.py`, `названия_импорт.py`) **отправляют текущие адреса фото заново** вместе с новыми. Если там
  ссылки GitHub, Ozon снова пойдёт на GitHub, и при мёртвой ссылке правка карточки может упасть или фото пропадёт.
  Проверить на 2–3 карточках выгрузкой `/v2/product/pictures/info` (только чтение) или спросить владельца/поддержку Ozon.

**Вывод-правило:** GitHub-репозиторий и ссылки raw.githubusercontent.com не удалять, не переименовывать, не делать
приватным и не переписывать историю, пока не доказано, что ни одна карточка на них не ссылается. Перенос в S3 добавляет
второе место хранения, а не заменяет первое.

## 5. Рекомендации GitHub по размеру

- Репозиторий желательно держать до 1 ГБ, настоятельно — до 5 ГБ; файл больше 50 МБ — предупреждение, больше 100 МБ — отказ.
  GitHub — не файловый хостинг и не CDN: при большом размере или трафике он вправе ограничить репозиторий, а raw-ссылки
  имеют ограничения на частоту запросов.
- setra-ozon-media уже около 3,3–3,8 ГБ и растёт примерно на 0,3–0,5 ГБ за волну инфографики (453 карточки × 2–3 файла
  × 120 КБ ≈ 0,15 ГБ; волна на 850 карточек ≈ 0,3 ГБ). До 5 ГБ осталось несколько волн. Каждая замена файла
  (как «DENSO ZXE24HLR7: обложка…») оставляет старую версию в истории навсегда.

## 6. План переноса в S3 Timeweb Cloud

### Шаг 0. Подсчёт (Claude, только чтение)
Скрипт выгружает `/v2/product/pictures/info` по всем товарам магазина и считает: сколько карточек и фото ссылаются на
`setra-ozon-media`, а сколько уже на `ozone.ru`. Это сразу отвечает на вопрос из раздела 4.

### Шаг 1. Что делает владелец в панели Timeweb сам
1. «Хранилище S3» → «Создать хранилище»: тариф по объёму (с запасом, от 10 ГБ), регион — тот же, что у приложения;
   имя, например, `setra-ozon-media`; **тип — публичное** (чтение всем, запись только по ключу).
   Timeweb может добавить к имени свою приставку — точное имя бакета и адрес сохранить.
2. Записать с карточки бакета (это не секреты): имя бакета, адрес S3 (у Timeweb — `https://s3.twcstorage.ru`,
   в старых бакетах `https://s3.timeweb.cloud`; брать тот, что в панели), регион (обычно `ru-1`).
3. Ключи доступа (Access Key и Secret Key) из той же карточки владелец **сам** вписывает в файл
   `~/setraparts/ozon/.s3.env` (строки `S3_ACCESS_KEY=…`, `S3_SECRET_KEY=…`, `S3_BUCKET=…`, `S3_ENDPOINT=…`,
   `S3_REGION=…`). В чат ключи не присылать. Файл в Git не добавлять.
4. Проверить в браузере одну тестовую ссылку после первой заливки (Claude даст адрес).
5. По желанию позже — свой поддомен (например `media.setraparts.ru`) через CNAME на бакет: тогда ссылки не зависят от
   провайдера. Делать до массовой перепривязки карточек, если вообще делать.

### Шаг 2. Скрипт `media_s3_sync.py` (Python, только стандартная библиотека)
Место: `setra-parts-claude-workspace/tools/media_s3_sync.py`.
- Ключи: окружение → `.s3.env`; в вывод и журналы не печатаются (как в `ozon_api.py`).
- Подпись AWS Signature V4 (`hmac`, `hashlib`), сервис `s3`, заголовок `x-amz-content-sha256` = SHA-256 тела;
  ключ объекта кодируется по правилам S3 (UTF-8, `%20`, слэши не кодируются) — 96 путей с пробелами и кириллицей.
- Ключ в бакете = путь в репозитории (`photo/infographics/X/01.jpg`, `video/X.mp4`). Тогда новая ссылка =
  `<адрес бакета>/` + тот же путь, меняется только приставка.
- Перед заливкой — список объектов бакета (`ListObjectsV2`, постранично по 1000) → размер и ETag каждого.
  Файл пропускается, если размер совпал и ETag = MD5 локального файла (у обычной, не составной загрузки ETag — это MD5).
  Режим `--быстро`: сравнивать только размер.
- Загрузка `PUT` с `Content-Type` (image/jpeg, video/mp4), `Cache-Control: public, max-age=31536000`,
  `x-amz-acl: public-read` (если бакет публичный целиком — не обязателен). 4–8 потоков, повтор при 5xx/429 с паузой.
- **По умолчанию — пробный прогон** (`--dry-run`): только печатает, сколько файлов и МБ будет залито/пропущено.
  Запись — только с `--apply`. Фильтр `--prefix photo/infographics/` и `--list волна.json` (залить только файлы волны).
- После заливки — проверка: выборочно (или `--verify-all`) `HEAD` по публичной ссылке без ключа: код 200, тот же размер.
- Журнал `s3_sync_<дата>.json`: залито / пропущено / ошибки. Повторный запуск дозаливает только недостающее.
- Тесты: подпись сверяется с эталонным примером AWS (как сделано для Postbox), кодирование ключей с пробелом и кириллицей.

### Шаг 3. Первичная заливка
`--dry-run` → показать владельцу итог (≈31 тыс. файлов, ≈3,8 ГБ) → `--apply` с его согласия → `--verify-all`.
GitHub остаётся как есть.

### Шаг 4. Новые волны — сразу в S3
- В генераторе инфографики (найти на Маке, раздел 1) и в `korrektor_more.py` заменить жёсткую ссылку на переменную
  `SETRA_MEDIA_BASE` (по умолчанию пока GitHub, после проверки — адрес бакета + `/photo/`).
- Порядок волны: сгенерировать файлы в локальную папку той же структуры → `media_s3_sync.py --apply --list <волна>.json`
  → проверка ссылок (`korrektor_more.py` уже скачивает ссылку перед отправкой) → только потом отправка в Ozon.
- В Git картинки новых волн больше не коммитить. Локальная папка остаётся рабочей копией; при желании в Git хранить
  только списки волн (json) и журнал заливки.

### Шаг 5. Старые карточки — не трогать, пока не нужно
- Существующие карточки продолжают работать: ссылки GitHub живы, а покупатели видят копию Ozon на ir.ozone.ru.
- Перепривязывать старые карточки на S3 только если шаг 0 покажет, что Ozon хранит и пересылает исходные ссылки GitHub.
  Тогда — постепенно, при плановых правках: корректор заменяет в списке фото приставку
  `raw.githubusercontent.com/.../main/` на адрес бакета (путь тот же), с откатом в `ОТКАТ_korrektor_фото_*.json`,
  пачками и с проверкой модерации. Отдельной массовой перезаливки фото ради переезда не делать.
- GitHub-репозиторий заморозить (не пушить картинки), но **не удалять** минимум до тех пор, пока выгрузка не покажет
  ноль ссылок на setra-ozon-media во всех карточках.
